# 케이스 스터디 (8D) — 알람 이후 무엇을 어떤 순서로 했는가

> **전부 합성 시나리오다.** 두 케이스의 웨이퍼 맵·판정·관리도·이벤트는 `wm811k_spc.py --demo`가 만드는 합성 시퀀스(그리고 그것을 아래 스니펫으로 변형한 시퀀스)에서 나온 것이고, "장비 측 증거"(RF 카운터·보정값·He 압력·티칭 로그)는 시나리오를 위해 지어낸 값이다. 실제 고객·장비·로트 데이터가 아니며, 특정 TEL 장비의 내부 구조나 매뉴얼을 전제하지 않는다. 탐지 시점·알람 수 같은 숫자는 로직 확인 결과이지 탐지 성능이 아니다. 고객 보고서 예문의 로트명·장비 ID는 가상이고 익명화 표기(`--anonymize`와 같은 16자리 해시 형식; 같은 사안의 세 보고가 같은 ID를 쓰도록 키는 환경변수 `WM811K_ANON_KEY`로 고정한다)를 쓴다.

이 문서가 답하려는 질문은 하나다. "관리도가 울렸다. 다음 30분, 다음 24시간, 종결까지 무엇을 했고 무엇을 남겼나." 절차 자체는 [`defect_signatures.md`](defect_signatures.md)의 현장 순서 8단계와 [`handoff.md`](handoff.md)의 보고 3단계에 있고, 여기서는 그 절차를 합성 데이터 위에서 끝까지 한 번 수행한 기록을 8D 양식으로 적는다. 관리도의 설정·규칙·수치 표는 [`spc.md`](spc.md)에 있다.

**재현 명령** (이 문서의 모든 숫자는 아래 세 실행과 `--demo` 두 종류의 출력에서 가져왔다; 실행 환경은 Linux, `MPLBACKEND=Agg`, 각 3~4초):

```bash
python wm811k_spc.py --demo --group-col chamber --event-col event --output spc_demo_group   # 탐지 구간 (케이스 A·B 공통)
python wm811k_scratch_shape.py --demo --output scratch_demo                                 # 케이스 B 모양 판별
python wm811k_azimuth.py --demo --output azimuth_demo                                       # 케이스 B 각도 재현성 판정의 로직
```

데모 시퀀스에는 조치 후 복귀가 없다(드리프트·계단이 끝까지 이어진다). 조치 후 복귀(D6)는 데모 시퀀스를 웨이퍼 5000까지 그대로 두고 그 뒤만 바꾼 변형 시퀀스로 보였다. 변형은 다음 스니펫 하나다(탐지 구간 수치는 데모와 동일하다). 재현 순서: 저장소 루트에서 스니펫을 `make_case_ab.py`로 저장해 `python make_case_ab.py`(→ `case_ab.csv`) 다음 `python wm811k_spc.py case_ab.csv --group-col chamber --event-col event --output case_spc` 두 줄이다. 산출물·`case_ab.csv`는 커밋하지 않는다(`.gitignore`가 `*.csv`를 막는다):

```python
import numpy as np, pandas as pd, wm811k_spc as spc
df = spc.demo_predictions()                       # --demo 와 같은 시퀀스 (시드 3)
rng = np.random.default_rng(2026)
base = np.array(spc.WM811K_COUNTS, float); base = base / base.sum() * (1 - spc.DEMO["clean_frac"])
er, sc = base[spc.CLASSES.index("EDGE_RING")], base[spc.CLASSES.index("SCRATCH")]
er_b = er + spc.DEMO["clean_frac"] * spc.DEMO["drift_mag"]
sc_b = sc + spc.DEMO["clean_frac"] * (1 - spc.DEMO["drift_mag"]) * spc.DEMO["step_mag"]
B = df["chamber"] == "B"
idx = df.index[B & (df["sample_id"] >= 5000) & (df["y_pred"] == "EDGE_RING")]   # 5000: 엣지 링 교체 -> 초과분 제거
df.loc[idx[rng.random(len(idx)) > er / er_b], "y_pred"] = "CLEAN"
m = B & (df["sample_id"] >= 5000); df.loc[m, "confidence"] = rng.beta(8, 1.2, size=m.sum())
idx = df.index[B & (df["sample_id"] >= 5050) & (df["y_pred"] == "SCRATCH")]     # 5050: 엔드이펙터 패드 교체 -> 초과분 제거
df.loc[idx[rng.random(len(idx)) > sc / sc_b], "y_pred"] = "CLEAN"
df["event"] = ""
df.loc[df["sample_id"] == 1025, "event"] = "pm_wet_clean"
df.loc[df["sample_id"] == 2900, "event"] = "pm_wet_clean"            # 데모의 'focus_ring_replaced' 를 PM 기록으로 바꿈
df.loc[df["sample_id"] == 5000, "event"] = "focus_ring_replaced"
df.loc[df["sample_id"] == 5050, "event"] = "endeffector_pad_replaced"
df.to_csv("case_ab.csv", index=False)
# python wm811k_spc.py case_ab.csv --group-col chamber --event-col event --output case_spc
```

변형 시퀀스의 B 챔버 구간별 발생률(검증용): 0-2999 EDGE_RING 0.057 / SCRATCH 0.011 / 저신뢰 0.097 → 3000-3999 0.104 / 0.008 / 0.166 → 4000-4999 0.142 / 0.116 / 0.380 → 5000-5999 0.044 / 0.016 / 0.116.

### A-2. 5-why

1. 왜 B 로트의 엣지 다이가 죽었나 → 챔버 B의 엣지 식각률이 중심과 달라졌다(엣지 링 패턴, 로트 전체에 반복).
2. 왜 엣지 식각률이 달라졌나 → 웨이퍼 가장자리에서 시스가 휘어 이온 입사각·식각률이 변했다(엣지 링 마모 시 생기는 일반 물리; 보정값이 상한에 닿아 더 보정하지 못함).
3. 왜 보정 한계에 닿았나 → 엣지 링이 소모 수명에 이르렀다(누적 RF 시간 카운터가 교체 기준 근접).
4. 왜 수명에 이른 링이 장착돼 있었나 → 2900 PM 때 교체 판단을 육안 검사로 했고, 마모는 육안으로 보이지 않았다.
5. 왜 육안으로 판단했나 → 교체 절차서에 RF 카운터 기준이 없었다(관리 체계 문제 → D7).

### B-2. 5-why

1. 왜 B 로트에 선형 불량이 반복되나 → 웨이퍼가 같은 방향·위치로 긁혔다(직선, 노치 기준 각도 재현 → 고정 접촉).
2. 왜 고정 접촉이 생겼나 → B 측 핸드오프에서 웨이퍼가 엔드이펙터 위에서 미끄러져 끌렸다(슬립 감지 알람 2건).
3. 왜 미끄러졌나 → 엔드이펙터 패드가 마모·오염돼 마찰이 떨어졌다.
4. 왜 마모된 패드가 그대로 있었나 → 패드 교체가 '이상 시'로만 돼 있어 매수 기준이 없었다.
5. 왜 기준이 없었나 → 반송계 소모품을 PM 체크리스트에 넣지 않았다(관리 체계 → D7).

### B-3. Ishikawa 6M 한 줄

Machine(엔드이펙터 패드 마모 → 슬립) ← **채택** / Method(패드 교체 기준 없음) ← 근본 원인 / Material(패드 재질 — 미확인) / Measurement(직선·호 판별은 경험칙이라 `ambiguous`가 나오면 육안·현미경으로 보강) / Man(티칭 변경 없음 → 배제) / Environment(CMP는 A/B 공통이고 호 아님 → 타사 인계 불필요).

## 두 케이스에서 배운 것 (이 저장소에 반영된 것과 남은 것)

- **층화가 탐지 시점을 앞당긴다**: EDGE_RING 드리프트는 전체 관리도 EWMA 3899 → 챔버 B 관리도 3774. 그룹 간 카이제곱 p가 baseline 0.75 → 감시 < 0.0001로 바뀐 것이 "챔버 B 문제"의 첫 근거였다.
- **드문 패턴은 부분군이 커서 느리다**: SCRATCH는 475장. 조치 검증은 관리도를 기다리지 말고 원시 비율 검정으로 먼저 한다.
- **EWMA는 기억이 있어 복귀가 느리다**: 큰 이탈 뒤에는 λ 0.2에서 4~5 부분군이 지나야 한계 안으로 돌아온다. 조치 시점에서 EWMA를 재시작하는 옵션은 아직 없다([`roadmap.md`](roadmap.md)).
- **허위 알람은 있다**: 같은 실행에서 심지 않은 EDGE_RING@A(R1 4399), LOW_CONFIDENCE@A(R1 5799), LOC@B(5974, 마지막 부분군 n=300)에 상승 알람이 났다. 131개 감시 점 중 3점. 앞의 둘은 R1 1점뿐이라 보고서가 `단발`로 표시하고 점검 목록 대신 다음 부분군 확인을 권한다. LOC@B는 baseline 부분군이 3개뿐이라 중심선 추정이 약했고, 변형 시퀀스에서는 이 허위 알람이 우연히 `endeffector_pad_replaced` +924장으로 찍혔다 — 이벤트 거리는 상관이지 인과가 아니다.
- **규칙 완성점의 방향 표기**: R3·R4는 창이 완성되는 점에 표시되는데 그 점의 z 부호로 방향을 정하므로, 상승 창이 하강점에서 완성되면 `down`으로 기록된다(변형 시퀀스 EDGE_RING@B 5174 R3). 창 안 다수 점의 부호로 정하는 편이 맞다([`roadmap.md`](roadmap.md)).
