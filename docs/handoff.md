# 협업·인계 — TEL 원인 vs 타사 인계, 고객 보고 3단계, 8D 팀 구성, 기밀 취급

> 한 줄 요약: 장비사 기술지원 엔지니어가 고객 에스컬레이션을 받았을 때 "우리 장비 원인인가, 타사 장비 인계인가"를 가르는 패턴별 기준, 고객 보고 3단계, 8D D1 팀 구성에서의 역할, 고객 데이터 기밀 원칙을 적는다. **이 저장소는 1인 프로젝트이며, 아래 협업 구조는 공개 자료(채용 공고의 업무 서술, 8D 일반 절차) 기준의 설계이지 실제 조직 경험이 아니다.**

## 1. 패턴별 'TEL 원인 vs 타사 장비 인계' 판정 기준

판정은 맵 한 장이 아니라 **로트 이력(어느 챔버를 거쳤는가)과 장비 측 증거(알람 로그·부품 카운터·PM 이력)를 맞댄 뒤**에 난다. 아래는 `wafer_pattern_classifier.ACTION_DETAIL[*]['handoff']`와 같은 내용을 표로 옮긴 것이다. 어느 쪽도 아니면 '보류 - 추가 데이터 요청'이 답이지 억지로 가르지 않는다.

| 패턴 | TEL 원인으로 보는 근거 | 타사 인계로 보는 근거 | 인계 대상(타사) |
|---|---|---|---|
| EDGE_RING | 링 폭 변화 시점이 TEL 식각 챔버의 엣지 링 RF 카운터·보정값 한계·PM 시점과 겹침; 성막 히터 엣지 존·코터 EBR 폭 설정 변경과 일치 | 로트 이력에서 CMP 직후 로트에만 생김, TEL 챔버 통과/비통과 로트 간 비율 차 없음 | CMP(리테이닝 링 - 엣지 제거율 프로파일 이탈) |
| EDGE_LOC | 노치 기준 각도가 TEL 챔버 도면의 배기·가스구 위치나 로봇 센터링 오프셋 로그와 맞음; 코터 EBR 편심 측정값 | TEL 장비를 안 거친 로트에서도 같은 각도가 재현됨 | 해당 각도를 만드는 타사 장비의 반송계·챔버 |
| CENTER | 중심 원 반경이 TEL 챔버의 ESC/히터 중심 존 반경·노즐 설정과 맞고 그 챔버 로트에만 나옴 | CMP 직후 로트에만 나옴(다존 헤드 중심 존) | CMP |
| DONUT | 고리 반경이 TEL 장비의 히터/ESC 존 경계와 일치 | 고리 반경이 CMP 헤드 존 반경과 일치하고 CMP 직후에만 나옴 | CMP |
| SCRATCH | 로트 안에서 선의 방향·위치가 노치 기준으로 재현되고 TEL 반송 경로(EFEM 로봇·FOUP 슬롯)와 맞음; 코터 방사선·소용돌이 서명 | 호 모양·무작위 위치·CMP 직후 로트(경험칙 - 절대 규칙 아님) | CMP(슬러리·패드·컨디셔너·링 홈; CMP 일체형 후세정 브러시). 프로브 카드의 정상 터치다운은 선형 스크래치를 만들지 않지만, 다이 격자 축에 평행한 직선이 재테스트 후에도 남으면 프로버 Z·인덱스 점검(TEL 프로버 Precio / Prexa면 TEL 범위, 아니면 해당 프로버 벤더) [26] |
| LOC | 위치가 TEL 챔버의 리프트 핀 반경(같은 반경 3점, 120°)·시즈닝 이력·PM 직후 파티클과 맞음 | 샷(노광 필드) 피치로 반복(레티클 리피터); 다이 피치 반복은 공정 마진; 터치다운 격자 반복이면 프로버(TEL Precio/Prexa면 TEL 프로버 지원, 아니면 해당 벤더) | 노광·레티클, 타사 프로버 |
| RANDOM | 특정 TEL 챔버 통과 로트에서만 밀도가 오르고 그 챔버의 시즈닝·PM 시점과 겹침 | 모든 경로에서 고르게 오름(라인 청정도); 단계별 인라인 파티클 추세가 타사 단계를 가리킴 | 인라인 검사 데이터를 가진 고객 설비팀·해당 단계 벤더 |
| NEAR_FULL | 재테스트 후에도 전면 불량이고 로트 이력의 비정상 종료가 TEL 장비 알람과 겹침; 프로버가 Precio / Prexa면 접촉 조건(오버드라이브·Z·평탄도 보정·클리닝 레시피·척 온도·프로브 마크 검사)은 TEL 범위 | 재테스트로 사라짐(테스트 프로그램·테스터; 프로브 카드 자체 — 니들·CRES·수명 — 는 카드 벤더·고객 테스트팀), 타사 공정 장비의 비정상 종료 | 테스터·테스트 프로그램, 프로브 카드 벤더, 타사 공정 장비 |

인계할 때 TEL 쪽이 넘기는 것: 판정 근거(위 표의 해당 행), TEL 챔버 로트/비통과 로트 비율 비교(`wm811k_spc.py --group-col` 카이제곱 출력), 알람 시작점과 TEL 이벤트의 거리(`--event-col`), TEL 장비 측 로그에 이상이 없다는 기록. "우리 장비가 아니다"를 증거 없이 말하지 않는다.

## 2. 고객 보고 3단계

| 단계 | 시점 | 담는 것 | 이 저장소의 출력 |
|---|---|---|---|
| 초동 보고 | 에스컬레이션 수신 후 첫 보고(같은 날, 가능하면 수 시간 내 - 추정) | 현상(패턴·영향 로트·웨이퍼 수·불량률), 심각도(`ACTION_DETAIL` severity: 모니터링 / 로트 홀드 검토 / 라인 정지 판단 필요), 먼저 배제할 것(재테스트 등), 봉쇄 조치 제안(로트 홀드·챔버 격리 여부), 요청 데이터 목록(`data_to_collect`), 다음 보고 시각 | `wafer_pattern_classifier.py --actions <패턴>`, SPC 알람 요약 보고서 `spc_<stem>_report.md`, 배치 PDF |
| 중간 보고 | 정해진 주기(일 1회 또는 교대당 1회 - 고객과 합의, 추정)와 상태 변화 시 | 확인한 것/배제한 것(고객 측 증거·장비 측 증거별), 남은 가설, 임시 조치 효과(관리도에서 비율이 내려가는가), 부품 수배·PM 일정, 타사 인계 여부와 근거 | 층화 관리도(`--group-col`), 이벤트 거리(`--event-col`), 재테스트 전후 맵 |
| 종결 보고 | 근본 원인 확정·시정 조치 후 관리도가 중심선으로 복귀했을 때 | 근본 원인(5-why 체인), 시정 조치(부품 교체·레시피·티칭), 효과 확인(조치 후 부분군 N개에서 알람 없음·p가 중심선 복귀), 재발 방지(카운터 기준·PM 항목 추가·관리도 상시화), 교체 부품의 누적 카운터 값, 남은 리스크 | 조치 전후 관리도 PNG, alarms.csv의 acknowledged_at / action / verified_at 열 |

보고서는 사실(측정값·로그)과 추정(가설)을 줄 단위로 구분해 적는다. 고객이 읽는 문서이므로 통계 용어(z, R1~R4)는 설명 열을 붙인다.

## 3. 8D D1 팀 구성에서의 역할 (공개 자료 기준 설계)

| 역할 | 담당 | 이 문제에서 하는 일 |
|---|---|---|
| 고객 수율팀 | 고객 | 빈 맵·수율 집계·로트 이력·재테스트·인라인 검사 추세 제공(고객 측 증거), 로트 홀드·라인 정지 결정권, 타사 벤더 호출 |
| TEL FE (Field Engineer) | TEL 현장 | 장비 측 증거 추출(알람 로그·부품 카운터·PM 이력·로봇 로그), 점검·부품 교체·티칭, 작업지시서·보고서 작성, 긴급 부품 수배 [53][54] |
| TEL PE (Process Engineer) | TEL 현장/평가 | 레시피·공정 조건 관점의 원인 분석, 평가 웨이퍼로 재현 실험, 공정 셋업·트러블 대응 [53][54] |
| 기술지원(소프트웨어·데이터) | TEL 현장 | 이 저장소에 해당: 맵 판정·관리도·층화·이벤트 대조를 돌려 FE/PE가 볼 가설 순서를 좁히고 보고서 초안을 만든다. 장비·분석 소프트웨어에 장애가 나면 5절의 에스컬레이션 패키지를 만든다 |
| 본사·해외 법인 | TEL 본사 | 부품·설계 정보, 유사 사례, 특허·사양 수준의 기술 판단, 설계 변경(CIP) [53][54]. 언제·무엇을 올리는지는 아래 소표 |
| 타사 장비 벤더 | 고객이 호출 | 인계 항목(CMP·노광·테스터)의 자기 장비 측 증거 |

D2(문제 정의)는 패턴·영향 로트·손실 다이 수, D3(봉쇄)는 로트 홀드·재테스트·챔버 격리, D4(근본 원인)는 위 1절 판정과 5-why, D5~D7은 2절 종결 보고 항목과 같다. 협업 축으로 보면 FE가 장비, PE가 공정, 고객이 결과를 각각 소유하고, 기술지원 소프트웨어는 세 데이터를 같은 시간축에 놓는 역할이다.

## 4. 고객 데이터 기밀 취급 원칙

- 저장소에는 **공개 데이터(WM-811K)와 합성 데이터만** 둔다. 고객 빈 맵·로트명·레시피·장비/챔버 ID·수율 수치는 커밋하지 않는다(`.gitignore`가 `*.csv`, `test_predictions.csv`, `*.lot_history.csv`를 막는다).
- 리포트·관리도에는 익명화 옵션을 쓴다: `wm811k_spc.py --anonymize`는 로트명·그룹 ID를 짧은 해시로 치환하고 매핑 표를 저장하지 않는다. `wm811k_lot_report.py --anonymize`는 로트명과 장비·챔버 ID를, `wm811k_commonality.py --anonymize`는 lot/tool/chamber 를 같은 방식으로 치환한다.
- 같은 사안의 보고 3단계(초동·중간·종결)에서 ID 가 서로 대조되려면 같은 키로 익명화해야 한다. `wm811k_spc.py`는 `WM811K_ANON_KEY` 환경변수(또는 `--anon-key-env`)를 키로 쓰고, 로트 리포트·공통성 분석은 아직 실행마다 새 키를 쓴다(같은 키 옵션으로 통일하는 것은 `docs/roadmap.md`의 남은 항목). 키는 저장소·보고서·로그에 넣지 않는다.
- 샘플 리포트·케이스 스터디는 전부 합성 시나리오임을 문서 상단에 적는다.
- 고객 팹 안에서 본 것은 허가 범위 밖으로 가져오지 않고(사진·화면 캡처 포함), 본사 공유도 고객 승인 범위 안에서만 한다. 이 원칙은 NDA 일반 관행 수준이며 실제 계약 조건은 고객·TEL 규정이 우선한다.

## 5. 소프트웨어 장애 에스컬레이션 패키지

직무명의 '소프트웨어' 쪽이다. 장비 소프트웨어(장비 제어·데이터 수집·원격 모니터링 클라이언트)나 이 저장소 같은 분석 도구가 고객 PC·장비 PC에서 멈추거나 틀린 값을 낼 때, 현장이 수집해 본사 소프트웨어 조직에 올리는 묶음을 정해 둔다. 일반 소프트웨어 지원 관행 수준의 설계이며 TEL 내부 절차·티켓 체계는 모른다.

| 항목 | 수집하는 것 | 이 저장소에서의 대응 |
|---|---|---|
| 제품·버전 | 장비 소프트웨어 제품명·버전, OS·런타임 버전(Python 버전, 주요 패키지 버전), 설치 경로, 마지막 업데이트일 | `requirements.txt` 고정 버전, `results/environment.txt`(실측 환경 기록 양식) |
| 설정·레시피 스냅샷 | 장애 시점의 설정 파일·레시피·환경변수(예: `WM811K_DIR`), 변경 이력(누가·언제) | 관리도 설정(부분군 크기·EWMA·group/event 열·익명화 여부)을 보고서 머리에 기록(`spc_<stem>_report.md`의 '설정' 줄); 전체 명령행은 작업 기록에 따로 적는다 |
| 로그 시간창 | 장애 전후의 알람·이벤트 로그, 애플리케이션 로그, OS 이벤트, 콘솔 출력(`stderr` 포함) — 증상 시각 기준 전후 창을 정해 자른다 | 콘솔은 UTF-8로 재설정하고(`sys.stdout.reconfigure`), 문구는 cp949 안전(`tests/test_actions.py::test_strings_are_cp949_safe`)이라 Windows 리다이렉트 로그가 깨지지 않는다 |
| 재현 절차와 재현 여부 | 입력 파일(익명화), 실행한 명령, 기대 결과 vs 실제 결과, 재현 횟수/조건(항상·간헐·특정 입력에서만) | `--demo`(합성 입력)로 같은 명령을 돌려 도구 자체 문제인지 입력 문제인지 가른다; 종료 코드(`wafer_pattern_classifier.py` 자체 검증 실패 1, 정상 0)로 자동 판별 |
| 타임라인·영향 범위 | 첫 증상 시각, 직전 변경(업데이트·설정·OS 패치), 영향 장비·로트·사용자 수, 우회 중인지 | 중간 보고 양식(2절)과 같은 칸 |
| 1차 조치 기록 | 재현 → 우회(다른 PC·이전 버전·`--lang en`·폰트 폴백) → 롤백(버전 고정 재설치) 순서로 무엇을 했고 결과가 무엇이었는지 | 한글 폰트 없으면 그림만 영문으로 자동 전환(`_fonts.py`), 폰트 동봉(`docs/fonts/`) |
| 반출 범위 | 고객이 승인한 범위(로그에 로트명·레시피가 섞이면 익명화 또는 제외), 승인자·일시 | `--anonymize`, 4절 기밀 원칙 |

본사로 올리는 기준: (a) 재현되는데 현장 우회·롤백으로 안 풀릴 때, (b) 틀린 값(판정·수치)이 의심될 때 — 입력과 기대값을 붙여서, (c) 간헐 장애가 같은 조건에서 2회 이상, (d) 보안·데이터 손상 의심은 즉시. 올릴 때는 위 표의 항목을 전부 채우고 '재현 여부'가 비어 있으면 올리지 않는다(재현 안 되는 보고는 본사에서 처리할 수 없다).

이 저장소를 고객 PC에서 돌리는 방법: `requirements.txt`로 설치 후 `--demo`가 전부 도는지 확인하는 것이 설치 검수이며, CI 매트릭스(ubuntu/windows × Python 3.11/3.12)가 같은 검수를 매 커밋 수행한다. 통합 CLI(`python -m wm811k`)와 Dockerfile은 [`roadmap.md`](roadmap.md) 7·8의 남은 항목이다.
